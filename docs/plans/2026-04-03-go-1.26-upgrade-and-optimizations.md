# Go 1.26 Upgrade and Codebase Optimizations

**Date:** 2026-04-03
**Branch:** `feature/go-1.26-upgrade`
**Target:** Upgrade from Go 1.24 → Go 1.26 and apply relevant optimizations

## Overview

This project is a lightweight HTTP proxy that receives search queries, forwards them to SearXNG, and uses an LLM (via the OpenAI SDK) to synthesize a concise answer with citations. The codebase is clean and small — 7 packages, ~15 source files — so the upgrade is straightforward with a few concrete optimization opportunities.

---

## 1. Version Bumps (Required)

### 1.1 `go.mod`
- Change `go 1.24` → `go 1.26`
- Go 1.26's new `go mod init` default sets the `go` directive one version behind to encourage compatibility, but since we're intentionally upgrading, set it to `go 1.26` explicitly.

### 1.2 `Containerfile`
- Change `FROM golang:1.24-bookworm` → `FROM golang:1.26-bookworm`
- No other Containerfile changes needed — the multi-stage build, `CGO_ENABLED=0`, `-trimpath`, `-ldflags="-s -w"` are all still valid and optimal.

### 1.3 `go.sum` / dependency update
- Run `go mod tidy` after the version bump to ensure `go.sum` reflects any toolchain changes.
- Run `go get -u ./...` if we want to pull latest dependency versions (the `openai-go/v3` SDK). This is optional — decide based on whether there are breaking changes.

## 3. Run `go fix` to Modernize Code

Go 1.26 completely revamped `go fix` using the Go analysis framework. It includes dozens of modernizers that automatically update code to current idioms.

**Action:** Run `go fix -diff ./...` to preview changes, then `go fix ./...` to apply.

This is the single highest-value action — it may surface idiomatic improvements we'd miss manually, such as:
- Replacing `interface{}` → `any` (if any remain)
- Adopting newer stdlib patterns
- Modernizing error handling idioms

## 4. Concrete Optimization Opportunities

### 4.1 Performance: Green Tea GC (Free, Automatic)

Go 1.26 enables the Green Tea GC by default. This project handles HTTP requests with moderate allocation (JSON parsing, string building for prompts). Expected benefits:
- **10-40% reduction in GC overhead** for allocation-heavy request paths
- **Faster small object allocation** (specialized paths for objects < 512 bytes) — directly relevant to this project's allocation patterns (small structs, slices, strings per request)
- **Better memory locality** — benefits the prompt-building and JSON-decoding hot paths

**No code changes needed.** This is a free performance win from the runtime upgrade.

### 4.2 Stack Allocation for Slices (Free, Automatic)

Go 1.26's compiler is smarter about allocating slice backing stores on the stack. This project creates several slices per request:
- `results` slice in `truncateAndRenumber` (`service.go`)
- `promptSources` slice in `SearchAndSynthesize`
- `citedSources` slice in `SearchAndSynthesize`
- `validCitations` slice from `sanitizeCitations`

If the compiler can prove these don't escape, they'll be stack-allocated, reducing GC pressure. **No code changes needed.**

### 4.3 `testing/synctest` Package (Evaluate for Future Use)

Go 1.25 stabilized `testing/synctest` for deterministic testing of concurrent code. This project currently doesn't have goroutine-based concurrency in its business logic (the server uses goroutines only in `main.go` for `ListenAndServe`), so **this doesn't apply today**. However, if concurrency is added later (e.g., parallel search calls), `synctest` would be valuable.

**Action:** Note in plan, skip for now.

### 4.4 Container Base Image Review

- The current runtime stage uses `gcr.io/distroless/static-debian12:nonroot`. Verify this still works with Go 1.26 binaries (it should — distroless/static is libc-free).
- Consider pinning a specific digest for reproducibility, but this is a separate concern from the Go upgrade.

**Action:** Verify container builds and runs. No change to base image.

### 4.5 `go vet` / Static Analysis

Run `go vet ./...` after the upgrade. Go 1.26 may have new vet checks. This is a quick verification step.

## 5. Changes NOT Applicable to This Project

These Go 1.25/1.26 features exist but don't apply here:

| Feature | Why it doesn't apply |
|---|---|
| `encoding/json/v2` | Still experimental, not in stdlib by default. This project uses `encoding/json` for simple request/response encoding — v2 would be premature. Worth adopting in Go 1.27 when it becomes default. |
| `new(expr)` syntax | This project doesn't have patterns like `new(int64)` that would benefit from initialization. |
| Self-referential generic constraints | No generic types defined in this project. |
| `crypto/hpke` | No cryptographic operations in this project. |
| Goroutine leak detection | No complex goroutine patterns to debug. |
| SIMD package | No low-level computation. |
| Container-aware GOMAXPROCS | This is a single-process HTTP server, not a CPU-intensive workload. |
